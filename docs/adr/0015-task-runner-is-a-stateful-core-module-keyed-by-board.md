# 任务运行器是 core 内的有状态模块，任务状态以（画板, 任务节点）为键

任务队列的时序约定（任务目录与 `last_submitted` 派发时才落地、429 重试不重写、任务目录已写才记结局、取消的三条路径、读参考图期间取消不入队）原先由无测试的 `useRunner` hook 用四份并行状态（`queue` / `entries` / `preparing` / `statuses`）手工遵守，`core/run.ts` 四个函数之间的调用顺序才是真正的接口；任务状态又以任务节点 id 为键、不分画板，同一画板包导入两次会串状态与锁定。我们改为：core 提供有状态工厂 `创建运行器(端口) → { 提交, 重新生成, 取消(过滤), 设并发上限, 订阅(快照) }`，内部 async；`core/queue.ts` 并入，每个任务一条带显式状态（读图中 / 等待 / 退避 / 执行中）的记录，`prepareJob` / `prepareRegenerate` / `writeJob` / `executeJob` 成为内部件。端口为 `RunDeps`（其 `now` 加 `定时(ms, fn) → 取消` 构成时钟）、画板写入（ADR 0014 的 `apply(画板键, 系统变更)`，运行器只产出「提交记录」「运行结果」两种数据，结果节点 id 由编辑模块的 `newId` 生成）与日志；不设读画板、读设置的端口——画板由调用方在提交 / 重新生成时传入，网关地址、密钥、能力表、输出目录与画板文件名在提交时随任务固化，排队期间改设置不影响已排队任务。快照按画板分：`画板(键) → { 状态表, 锁定集 }`，另有全局运行指示行与待处理数；ADR 0014 环境里的「每块画板一个锁定集」取自这里。

关闭画板时运行器遗忘该画板：清掉它的状态，并把它的任务编号移出「本次运行经手过」的集合；重开后失败 / 已取消由任务目录的 `outcome.json` 给出（ADR 0010），没有记录即「已中断」。读参考图阶段的失败没有任务目录可依，重开后不再显示——此时 `last_submitted` 也未落地，节点本就是未提交态。

## Flash 运行策略

Flash 普通生成的 HTTP 拒绝（含 429）、坏响应或结果下载失败直接进入失败，不进入自动退避重发，不切模型。既有其他模型的 429 退避保持原策略。取消仍仅客户端不再等待与落盘，不宣称网关取消协议；幂等、Retry-After、任务查询继续未知。公开验收接口是运行器的提交/重新生成/快照。

## Considered Options

- **纯状态机 `step(状态, 事件) → { 状态, 副作用[] }` 加通用解释器**：与 ADR 0014「核心保持同步、纯」形式上更一致；但要保护的约定都是跨 `await` 的时序（写目录期间被取消、429 后不重写），会落进解释器而仍然测不到。否决；`run.ts` 已是 core 内接收端口的 async 先例，ADR 0014 的「同步、纯」只约束编辑模块。
- **保留 `queue.ts` 作内部纯件，运行器包一层**：队列只认任务编号，归属、`written`、退避状态仍得在外面并行维护，退避要从 `retries[id]` 反推。否决；`queue.test.ts` 的用例改写为经运行器公开接口的测试。
- **终态一律只读 `outcome.json`，内存只管活动状态**：读参考图失败时任务目录还没写，做不到。否决。
- **终态按任务编号存、跨画板键存活**：绕开了任务目录这个真源，且内存状态与 `outcome.json` 会各说各话。否决。
- **测试用 vitest `useFakeTimers` 而不注入时钟**：依赖全局打补丁，与 promise 微任务交错时不确定。否决。
- **派发时再取当前设置**：与参考图快照、能力表摘要的「提交即固化」口径不一致，还要多一个读设置端口。否决；用旧密钥派发失败的任务重新生成即可。

## Consequences

- 任务迁移、`queue_dispatch`、`rate_limit`、`download` 日志事件进诊断包，属对外契约；它们由运行器经日志端口发出，测试对关键迁移序列断言。
- 依赖 ADR 0014（#122）先落地：系统变更的形状由它定义。
